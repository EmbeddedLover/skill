# LLM 上下文导出

台账的核心用途之一：把已验证事实喂给 LLM，替代它的记忆。

## 为什么必须导出

LLM 对具体型号的引脚映射极易编造，小众或国产芯片尤其严重。它会用完全自信的语气给出错误的引脚号。

这类错误的特征是**难以察觉**：代码语法正确、能运行、无报错，只是硬件不响应。你会花数小时怀疑接线、怀疑模块损坏，最后发现是一个数字。

对策不是提醒它小心，而是**不给它回忆的机会**——把权威事实放进提示词，并明确禁止使用其它引脚。

## 导出规则

**只导出 `[实测]` 和 `[官方]`** — `[推测]` 条目全部过滤。导出推测内容等于把 LLM 自己的幻觉再喂回去，会形成自我确认的循环。

**必须包含版本信息** — 平台、固件、库版本。缺少版本，LLM 会套用其它版本的 API 写法。

**必须包含禁用引脚清单** — 只说"可以用哪些"不够。明确列出不可用的引脚及原因，否则 LLM 在需要更多引脚时会自行挑选。

**必须包含约束指令** — 用明确的祈使句限定行为，而不是描述性说明。

**按需裁剪** — 只导出与当前任务相关的外设。全量导出浪费上下文，也增加 LLM 混淆不同外设配置的概率。

## 导出格式

```text
## 硬件事实（权威，禁止推测覆盖）

开发板: {{型号 + 版本}}
主控:   {{芯片}}
平台:   {{平台 + 固件版本}}
库:     {{库名 + 版本}}
IO电平: {{如 3.3V}}

### 已验证可用引脚

| 外设 | 信号 | 物理脚号 | GPIO号 | 复用功能 | 证据 |
|------|------|----------|--------|----------|------|
| ... |

### 禁用引脚

| 物理脚号 | GPIO号 | 原因 |
|----------|--------|------|
| ... |

### 已知约束

- {{供电、带宽、组合限制等}}

### 已排除的错误假设

- {{曾被验证为错误的说法，防止重复}}

## 约束

1. 只能使用上表中列出的引脚。需要表中没有的引脚时，停下来问我，不要自行选择。
2. 引脚号、GPIO 号、地址、波特率等具体数值只能取自上表。不确定时明确说不确定。
3. 使用与上述固件/库版本匹配的 API。不确定该版本是否支持某写法时说明。
4. 生成代码后列出你用到的每个引脚及其来源行，供我核对。
5. 不要修改已验证可用的配置。
```

第 4 条是关键。要求 LLM 自陈引脚来源，能把隐蔽的编造变成可核对的清单——它无法为编造的引脚指出来源行。

## 使用建议

**每次新会话重新贴** — LLM 不记得上次会话的内容。

**改动后重新导出** — 台账更新后旧的上下文块已过期。

**官方例程优先** — 让 LLM 基于官方例程修改，而不是从零生成。官方例程是在这块板子上验证过的代码，这个属性比任何生成结果都可靠。

**先自己查表** — 导出的前提是台账里的信息由你从官方资料查证过。让 LLM 帮你填台账再导出给 LLM，等于绕了一圈把幻觉合法化。

## 收到 LLM 输出后的核对

按顺序检查：

1. 它用的每个引脚是否都在授权表内。
2. 引脚号与 GPIO 号是否对应正确（这两个数字最容易被张冠李戴）。
3. API 写法是否匹配当前固件版本。
4. 是否悄悄引入了表外的引脚或外设。

发现编造的内容，写入 `PITFALLS.md` 的"已排除的错误假设"表。同一个错误 LLM 会反复犯，记下来能在下次导出时直接堵住。
