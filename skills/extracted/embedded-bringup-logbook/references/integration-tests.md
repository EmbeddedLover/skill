# 组合验证

单外设逐个 `已验证` 之后必须做这一步，再进入功能开发。三个外设分别正常、一起上就出问题，在嵌入式里非常常见，且排查难度远高于单外设阶段。

跳过组合验证的代价：故障出现在功能开发阶段，此时代码复杂度已经很高，你会误以为是业务逻辑 bug。

## 验证顺序

两两组合先做，再全部一起。两两阶段发现的问题好定位；直接全上则回到了多变量状态。

```text
A → A+B → A+C → B+C → A+B+C
```

按此顺序，每步只引入一个新的相互作用。

## 检查项

### 引脚冲突

单独测试时另一个外设未初始化，冲突不显现。同时启用才暴露。

现象：后初始化的外设正常，先初始化的失效；或两者都不稳定。

对照 `PINMAP.md` 全表复查复用功能是否互斥。

### 总线争用

同一总线挂多个设备时的相互影响。

现象：单独访问都正常，交替访问出错；某设备响应变慢或偶发超时。

排查方向：地址是否唯一、速率是否被最慢设备限制、上拉阻值是否因多设备而不合适、总线上是否有设备拉住不放。

### 供电与电流尖峰

最容易误判为软件问题的一类。

现象：随机重启、屏幕闪烁或花屏、通信偶发失败、某个动作触发瞬间出错。

触发条件通常是负载突变：扬声器出声、电机启动、无线模块发射、屏幕背光点亮。

排查方式：换更强的供电（外部电源代替 USB）后现象是否消失。这是判定供电问题最快的手段。

累加峰值电流与供电上限比对，写入 `PINMAP.md` 供电预算。

### 内存与带宽

资源受限平台上的组合上限。视觉类板子尤其明显——摄像头、屏幕、音频、模型推理同时运行会争抢内存和总线带宽。

现象：帧率下降、卡顿、内存分配失败、运行一段时间后崩溃。

排查方向：降低分辨率或帧率后是否缓解；逐个关闭外设定位瓶颈。

### 时序与初始化顺序

外设初始化顺序可能影响结果。共用时钟、复位信号、或存在依赖关系时尤其明显。

现象：调换初始化顺序后行为不同。

一旦确认顺序敏感，把正确顺序写入台账——这是最容易在重构时丢失的知识。

### 中断与实时性

多外设同时产生中断时的相互阻塞。

现象：某外设响应延迟、数据丢失、音频卡顿或爆音。

排查方向：中断处理耗时是否过长、优先级设置。

### 长时间运行

短时测试通过不代表稳定。

现象：运行几分钟到几小时后崩溃、发热后行为改变、内存缓慢耗尽。

至少连续运行一段时间观察，覆盖发热后的状态。

## 记录

组合阶段发现的问题一律写入 `PITFALLS.md`，分类用 `多外设组合`，因为它们不属于任何单一外设。

同时在相关外设文档的"与其它外设的相互影响"表补一行，让以后单独查该外设时也能看到。
