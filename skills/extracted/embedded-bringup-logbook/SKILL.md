# 外设点亮台账

本技能不做一次性的原理图分析（那是 `schematic-pinmap-analyzer` 的职责），而是建立**随项目生长的台账**。核心目标：让"已被硬件验证过的事实"和"AI 或文档的推测"在文件层面彻底分开。

## 触发条件

用户执行 `/embedded-bringup-logbook`。典型场景：

1. **新板子初始化** — 建立 `PINMAP.md` 和 `PITFALLS.md` 骨架。
2. **新增外设** — 分配引脚、检查冲突、生成该外设文档。
3. **调通后回填** — 把实测参数写入台账，状态改为已验证。
4. **踩坑后固化** — 把教训写成规则条目而非流水日记。
5. **导出提示词上下文** — 生成可直接贴给 LLM 的权威事实块。

## 不可违背的核心规则

### 规则一：引脚表全局唯一

`PINMAP.md` 必须是单一文件。引脚冲突本质是跨外设问题，拆分到各外设文档会导致两边各自声称占用同一引脚而无人发现。任何引脚分配动作都必须先读取现有 `PINMAP.md` 全表再落笔。

### 规则二：证据等级必须标注

每条记录都要带来源标记，不允许无标记条目：

- `[实测]` — 在本人这块板子上跑通过，最高等级。
- `[官方]` — 来自厂商引脚图、原理图、官方例程、官方文档。
- `[推测]` — 来自 LLM 输出、论坛帖子、同类型号类推。**禁止**在未标注的情况下写入。

`[推测]` 条目在被实测验证前，不得进入导出给 LLM 的权威事实块。

### 规则三：写规格，不写日记

禁止叙事体（"今天调麦克风，一开始没声音，后来发现……"）。每条必须结论前置、可直接抄用。

失败的尝试要记录，但转写成规则形式：

- 正确：`GPIO37 不可用作 I2S 输入 — 已被板载摄像头复位占用 [实测]`
- 错误：`我试了 GPIO37 结果不行`

### 规则四：版本与日期置于文件头部

固件版本、SDK/库版本、工具链版本、记录日期必须写在文件顶部信息块，不得散落正文。缺少版本号的台账会在平台升级后静默变成误导信息。所有日期使用绝对日期（`YYYY-MM-DD`），不使用"上周""前几天"。

### 规则五：不编造具体数值

引脚号、GPIO 编号、电压、寄存器地址、I2C 地址、波特率、采样率、API 名称一律不得推测填写。信息缺失时写 `待核对`，并在该行备注需要查证的来源（手册页码、原理图网络名、需实测项）。

### 规则六：不主动创建空脚手架

只建用户当前用到的文件。禁止一次性生成十个空外设文档——空模板不会被填写，只会增加维护负担并稀释可信度。

## 工作流程

### 首次初始化

1. 询问并记录：板子型号与版本、主控芯片、开发平台与固件版本、供电方式。
2. 读取 `references/document-spec.md` 获取字段定义。
3. 从 `assets/PINMAP.md` 与 `assets/PITFALLS.md` 复制骨架到用户指定目录（默认项目根 `docs/hardware/`）。
4. 填入信息块，引脚表主体留空。**不预填任何引脚数据**，除非用户已提供官方引脚图并明确要求导入。
5. 提示用户：先完成最小可用验证（刷固件、串口打印、点灯）再接外设，否则后续故障无法定位。

### 新增外设

1. 读取现有 `PINMAP.md` 全表。
2. 读取 `references/conflict-checks.md`，按清单逐项检查：物理引脚重复、复用功能互斥、板载功能占用、电平域不匹配、总线地址冲突、供电预算超限。
3. 冲突或不确定时**停止并报告**，不得自行挑一个引脚了事。
4. 无冲突后写入 `PINMAP.md`，状态标 `待验证`。
5. 从 `assets/peripheral-template.md` 生成 `peripherals/<外设名>.md`。
6. 提示用户上电前完成 `references/preflight-checklist.md` 的物理检查。硬件接错可能不可逆，此步不可跳过。

### 调通后回填

1. 将 `PINMAP.md` 中该外设状态从 `待验证` 改为 `已验证`，补记验证日期与验证方式。
2. 在外设文档填入实测参数，证据标记升级为 `[实测]`。
3. 把过程中的教训按规则三转写成条目：外设专属的写入该外设文档的禁忌区，跨外设通用的写入 `PITFALLS.md`。
4. 在 `PINMAP.md` 变更记录追加一行。

### 判断坑归属

写入 `PITFALLS.md` 的条件是**不属于任何单一外设**：供电与掉压、刷固件与启动、工具链与 IDE、平台 API 变更、多外设组合冲突、电平域与共地。

只影响单个外设的写入该外设文档，避免通用文件膨胀成无法检索的杂物间。

### 组合验证

单外设全部 `已验证` 后，必须执行组合验证再进入功能开发。读取 `references/integration-tests.md`，重点覆盖引脚冲突、总线争用、供电尖峰（扬声器、电机类负载）、内存与带宽上限（摄像头叠加屏幕叠加音频）。

组合阶段发现的问题一律写入 `PITFALLS.md`。

### 导出 LLM 上下文

用户请求时，按 `references/llm-context-export.md` 生成上下文块。硬性要求：

- 只导出 `[实测]` 和 `[官方]` 条目，过滤全部 `[推测]`。
- 附带平台与固件版本。
- 包含明确的禁用引脚清单与约束指令。

## 输出文件结构

```text
docs/hardware/
├── PINMAP.md                  # 全局引脚分配表（唯一）
├── PITFALLS.md                # 通用坑清单（跨外设）
└── peripherals/
    └── <外设名>.md            # 用到才建
```

## PINMAP.md 固定表头

```text
外设 | 物理脚号 | GPIO号 | 复用功能 | 方向 | 电平域 | 板载占用风险 | 状态 | 证据 | 备注
```

## PITFALLS.md 固定表头

```text
分类 | 现象 | 根因 | 规则/对策 | 影响范围 | 证据 | 记录日期
```

## 参考文件

执行对应动作前必须读取：

- `references/document-spec.md` — 字段定义与取值约定
- `references/conflict-checks.md` — 引脚冲突检查清单
- `references/preflight-checklist.md` — 上电前物理检查
- `references/integration-tests.md` — 组合验证项
- `references/llm-context-export.md` — 上下文导出规范

## 边界

不做硬件设计、器件选型、BOM 成本、PCB 工艺、结构散热分析。不替用户判断未连接外设是否计划使用。不输出综合评分、泛泛建议或"如果你需要我还可以"之类的尾句。
