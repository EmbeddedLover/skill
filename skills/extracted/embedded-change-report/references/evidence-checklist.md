# 证据清单

用本清单判断报告能安全声称什么。配合 `information-source-map.md` 使用。

## 证据来源分类

写结论前，对关键信息分类：

- `自动发现`：从项目文件、Git、日志、产物、map/ELF 文件或仓库文档提取。
- `工程推断`：从路径、代码结构、模块名或嵌入式模式推断。
- `用户确认`：由用户或项目负责人明确说明。
- `待用户确认`：报告需要但当前缺失。

报告可以使用这四类信息，但不能把 `工程推断` 或 `待用户确认` 写成已验证事实。

## Git 证据

强证据：

- 明确的 commit 范围
- 相对 base 的 clean diff
- 变更文件列表
- diff stat
- commit message 或 issue ID
- `extract_git_evidence.py` 报告 `ok: true`
- 未跟踪文件已纳入范围，或已说明有意排除

弱证据：

- 用户只说“我改了一些文件”
- 工作区未提交且混有无关修改
- 只有 patch 片段，没有完整文件列表
- `extract_git_evidence.py` 报告 `ok: false`
- 请求的 commit 范围无效或含糊
- 存在未跟踪文件且未审查

报告措辞：

- 强证据：`根据 commit <hash> 到 <hash> 的 diff`
- 弱证据：`根据当前提供的变更片段`
- 脚本错误：`Git 证据采集失败，不能将空 diff 视为无变更。`

## 构建证据

强证据：

- 构建命令或工具链已知
- 日志显示成功或失败
- 已提取 warning/error 数量
- 已识别输出产物
- 相关时有 Flash/RAM 用量
- `extract_build_summary.py` 报告 `status: success`

弱证据：

- 用户只说“应该能编译”
- 旧构建日志无法对应当前 commit
- 部分日志缺少最终结果
- 构建解析器报告 `status: failed`、`ambiguous` 或 `unknown`
- 日志同时包含成功和失败标记

报告措辞：

- 强证据：`构建日志显示成功，产物为 ...`
- 弱证据：`未提供可对应本次变更的完整构建日志`
- 含糊状态：`构建日志同时存在成功和失败线索，需要人工复核，不能作为编译通过证据。`

## 静态分析证据

强证据：

- 工具和版本已知
- 精确命令或配置已知
- findings 数量和严重度已知
- 区分了新增问题和既有问题

弱证据：

- 只笼统声称已运行静态分析
- 报告无法对应项目版本

## 硬件验证证据

强证据：

- 板卡型号或硬件版本已知
- 固件产物已知
- 测试步骤已记录
- 附有串口/CAN/Modbus/VISA 日志
- pass/fail 标准已知
- timestamp 或 operator 已知

弱证据：

- “上板看起来正常”
- 没有日志
- 板卡版本未知
- 固件产物未知

不要仅凭 code diff 声称硬件验证通过。

## 通信证据

强证据：

- 协议版本或寄存器表已知
- 有 frame 示例或日志
- 已测试 timeout/retry/error 行为
- 已识别兼容性对端

弱证据：

- 只有 parser/driver 的代码变更
- 没有对端设备或总线日志

## 内存证据

强证据：

- map/ELF 前后对比
- Flash/RAM/stack/heap 限制已知
- 已识别最大符号变化

弱证据：

- 只有 binary size
- 没有 baseline
- 没有 MCU 内存限制

## 用户确认类证据

除非仓库中有明确记录，否则这些都属于用户确认项：

- 需求意图
- 缺陷优先级
- 根因接受
- 客户影响
- 发布批准
- 风险接受
- 硬件测试 pass/fail 接受
- 生产就绪度

## 证据缺口措辞

适当使用这些表述：

- `未提供构建日志，无法确认本次变更是否可编译通过。`
- `未提供上板验证记录，硬件行为仍需实测确认。`
- `当前仅能基于 diff 判断影响范围，不能替代回归测试结论。`
- `内存余量阈值未提供，因此仅记录用量变化，不判断是否满足发布要求。`
- `发布结论需要项目负责人或测试负责人确认。`
- `采集脚本返回错误，当前报告不能把该项作为自动发现事实。`
- `日志预览已做基础脱敏，但对外发布前仍需人工复核敏感信息。`
