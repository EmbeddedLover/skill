# 报告质量准则

面向评审或发布的报告定稿前，使用本准则检查。

## 必须通过

- 报告说明证据范围。
- 变更文件按模块分组。
- Git 和构建采集错误被明确呈现，没有被解释为空变更或成功。
- 存在未跟踪文件时已提及。
- 高风险嵌入式区域被明确标注。
- 验证声明有证据支持。
- 缺失证据没有被隐藏。
- 对外分享前已复核日志预览中的敏感信息。
- 风险和回滚具体到工程师可以执行。
- 结论与证据强度匹配。

## 优质报告特征

- 报告区分事实和工程推断。
- 构建、静态分析、硬件和通信证据分开描述。
- 文件路径和 commit ID 精确。
- 生成代码或受保护代码变更被单独指出。
- 内存影响在可用时包含 baseline 和 after 值。
- 通信变更在可用时包含 ID、register address、frame format 或 timeout behavior。
- 回滚说明要回退的 commit 或文件，以及可能的硬件状态问题。

## 危险信号

- 没有日志或用户验证却声称“测试通过”。
- 对 ISR、DMA、RTOS、boot、linker、flash 或 driver 变更说“无风险”。
- 只描述业务功能，遗漏硬件资源。
- 忽略构建日志中的 warning。
- 把构建成功当作运行时行为证明。
- 把含糊构建日志当作构建成功。
- 忽略采集 JSON 中的 `ok: false`、`status: failed`、`status: ambiguous` 或 `evidence_gaps`。
- 报告漏掉未跟踪的新 source/config 文件。
- 漏掉删除文件。
- 漏掉生成代码影响。
- 将无关工作区修改混成一个结论且没有提示。

## 最终结论校准

- 只有当 diff 评审和基础验证证据满足项目正常合入标准时，才使用“建议合入”。
- 当已有代码和构建证据，但硬件或回归证据不完整时，使用“可进入下一阶段验证”。
- 当高风险硬件相关变更缺少配套验证时，使用“暂不建议发布”。
- 当证据主要来自用户说明或局部 diff 时，使用“仅供变更说明”。
