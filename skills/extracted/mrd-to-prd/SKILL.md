# MRD 转 PRD

## 概览

使用本 skill 将上游市场/业务材料转换成可评审的 PRD。除非用户明确要求其它语言，否则默认输出中文。

## 工作流程

1. 判断用户要求的输出模式：
   - `MVP版`：聚焦最小可发布范围。
   - `完整版`：包含策略、范围、指标、功能细节、风险和路线图。
   - `研发交付版`：强调用户流程、需求细节、规则、状态、异常和验收标准。
   用户未指定模式时，默认使用 `完整版`。
2. 判断产品类型：
   - `软件/互联网产品`
   - `AI 产品`
   - `智能硬件/IoT/嵌入式产品`
   - `软硬结合产品`
3. 从 MRD 提取事实：目标用户、市场问题、机会点、业务目标、成功指标、范围、约束、竞品、依赖、风险和时间线。
4. 对照 `references/mrd-checklist.md` 判断信息完整度。
5. 只有当缺口会阻塞可用 PRD 时，最多提出 5 个澄清问题。轻微缺口继续推进，并标记为假设或 `TBD`。
6. 按 `references/mapping-rules.md` 将 MRD 事实转换为 PRD 需求。
7. 如果产品属于智能硬件、IoT、嵌入式、可穿戴、键盘、传感器或任意联网实体设备，读取 `references/smart-hardware-prd.md` 并加入必需的硬件开发章节。
8. 按 `references/prd-templates.md` 中的匹配结构起草 PRD。
9. 除非用户指定其它路径，否则默认保存到 `docs/prd/<slug>-prd.md`。`<slug>` 来自源 MRD 文件名或产品名。
10. 若仍有假设，文末必须保留 `待确认事项`。

## 参考文件

- 判断是否需要澄清问题时，读取 `references/mrd-checklist.md`。
- 将 MRD 内容转换成 PRD 章节前，读取 `references/mapping-rules.md`。
- 起草最终 PRD 前，读取 `references/prd-templates.md`。
- 产品包含实体设备、固件、嵌入式系统、配套 App、生产、认证或售后责任时，读取 `references/smart-hardware-prd.md`。

## 澄清规则

- 一次最多提出 5 个问题。
- 优先澄清目标用户、核心问题、成功指标、MVP 范围和交付约束。
- 智能硬件优先澄清硬件形态、关键部件、固件/通信、生产阶段、认证区域和目标成本。
- 不要询问 MRD 已经明确的信息。
- 用户要求快速草稿，或缺口不影响主干 PRD 时，带明确假设继续推进。

## 写作规则

- 保留 MRD 中的事实；不要编造市场数据、收入、截止日期、技术栈或合规约束。
- MRD 有足够依据时，将模糊目标转成可衡量需求；依据不足时标记为 `TBD`。
- 必须包含非目标，用于控制范围。
- 每个主要需求都要有验收标准。
- 区分产品决策和假设。
- 智能硬件 PRD 保持在需求和决策门槛层级。除非用户明确要求，不要写成详细器件选型表、BOM、工厂测试流程、认证计划或固件协议规格。
- 使用简洁的产品经理语言：清楚、具体、可评审。

## 输出要求

返回完整 PRD 草稿，不要返回头脑风暴笔记。默认保存到 `docs/prd/<slug>-prd.md`，并在最终回复中给出路径。输入 MRD 较薄时，输出可用的一版草稿，并附简短 `待确认事项`。
