# 工程师视角报告规则（Engineer-Facing Report Rules）

报告面向要接手或修改项目的嵌入式软件工程师，须帮他们回答：

- 这是什么项目？
- 软件如何组织？
- 执行从哪里开始？
- 哪些模块各负责什么？
- 我该在哪里改行为？
- 如何构建、烧录、调试、运行？
- 改动前有哪些风险或未知？
- 后续 AI 会话应先读什么，才能不用重新摸索就继续？

## 报告四原则（硬性，贯穿全文）

1. **中文标题**：章节标题用中文；`Project Picture` / `AI Handoff Summary` 等专有名作英文副标题/括注；证据标签 `CONFIRMED` / `INFERRED` / `UNKNOWN` / `CONFLICT` / `UNVERIFIED` 保留英文。
2. **图优先**：调用关系一律优先用 Mermaid 图表达，文字只做补充与工程后果。**每个模块至少 2 张图**（模块架构图 + 实现调用关系图）。每张图后 2–5 条工程后果。图节点必须对应真实 文件/函数/模块/状态/任务/队列/硬件边界。
3. **目录**：标题之后紧跟 `## 📑 目录`，用锚点链接到各章节。
4. **按模块分层**：主线为「总体架构 → 每个模块的架构 → 每个模块的实现 → 跨模块流程 → 横切关注点」；同类琐碎模块合并。

## 必备工程价值

不要只描述「有什么」，必须给出可落地的实现路径。对每个重要功能或模块，提供：用途、入口函数/命令、关键文件、依赖、验证方法。

## 图表要求

用图降低阅读负担。只有散文和大表的报告难以快速扫读。默认用 Mermaid（文本、diff 友好、AI 可复用、GitHub/VSCode/Typora 原生渲染）。每次最终报告都必须同时生成 HTML；Markdown 仍是事实来源，HTML 是派生产物（读 `html-report-output.md`，保持独立、保留证据、无需 dev server 即可打开）。

normal/deep 最终报告**必须**含：

- **总体架构图**：顶层分层、模块边界、平台分层、主要三方依赖。
- **运行时流程图**：启动、初始化、主循环/调度器/任务/线程/回调。
- **每模块**：架构图 + 实现调用关系图（共 ≥2 张）。
- **选定路径数据/控制图**：每条用户选定路径一张端到端调用关系图，或在合并图中体现。

图规则：

- 每个有意义的图节点必须对应真实 文件/函数/模块/状态对象/线程/队列/硬件边界/产物。
- 禁止只重复目录名、不展示控制/数据流的装饰性图。
- 保持每张图可读；过密就拆。
- 每张图后用 2–5 条说明工程后果。

## AI 可复用价值

最终报告也是未来 AI 工作的交接件。读完应快速知道：项目身份、选定路径、重要文件、运行时流程、状态归属、并发模型、风险、未知、常见改动从哪开始。

不要写成泛泛的高管摘要。必须含稳定锚点：项目根/相对根、构建运行命令与产物、关键文件及各自为何重要、选定路径（user/AI）、主运行时/调用流、核心状态载体与生产者/消费者、线程/任务/中断/定时器/回调模型、硬件/平台边界文件、编辑前需复核的风险与未知、绑定到文件/函数的下一步任务入口。保持紧凑，详细证据放后文章节。

## 深度工程分析要求

有源码时，先发现候选业务/技术路径，再问用户哪些需要深挖（除非用户已指定、授权 `auto` 或要求全量分析）。有用的路径要命名具体的 函数/回调/队列/中断/定时器/协议处理器/文件，以及它们之间交换的状态。

不要假设技术最复杂的路径就是用户最高优先级。路径选择是产品/工程语境决策。AI 可推荐，但用户拍板。

## 候选路径检查点

深挖前给一个简短检查点：

```text
候选路径：
1. <短标题> — <一句理由>
2. <短标题> — <一句理由>
3. <短标题> — <一句理由>

| 候选路径 | 为何重要 | 证据入口 | 下游模块 | 建议优先级 | 深挖成本/风险 |
```

候选路径可含：启动、UI 流程、网络/天气/云、BLE/WiFi/协议、传感器/外设访问、显示/输入管线、音频、存储/配置、固件升级、日志/诊断、构建/部署、安全/电源。

表后问一个直接问题：

```text
本轮深挖哪些路径？回复编号如 `1,3,5`；回复 `auto` 由我按变更风险与中心性选择；或回复 `full` / `all` / `全量分析` 覆盖所有有工程意义且有证据支撑的路径。
（选定路径将在「四、选定路径深挖」以端到端调用关系图展开。）
```

若用户已指定路径，跳过检查点并声明将按用户选定路径继续。
若用户回复 `auto`，标记为 `AI-SELECTED` 并声明选择标准。若用户回复 `full` / `all` / `全量分析`，标记为 `FULL-ANALYSIS`，覆盖所有核心模块和有工程意义的候选路径，重复或低价值路径可合并。

若当前界面支持结构化选择提示，用它选路径；否则用编号选项，避免用户复制长标题。

## 模块并行分析与多路径深挖

深度分析优先按**核心模块**拆分。识别核心模块后，若环境允许子代理且用户/系统授权使用子代理，则每个核心模块或合并模块组开启一个子代理。每个子代理只回答分配模块：模块职责、关键文件/入口、内部架构图、实现调用关系、输入输出数据流、状态归属、并发/事件、风险、验证和证据。主 agent 必须复核并把结果**合并进一份最终报告**，去重共享架构，标注冲突或未知。

当用户选定多条跨模块路径时，可额外按路径开启子代理补充端到端调用链。路径子代理不得替代模块子代理；最终仍由主 agent 合并成一份 Markdown 和一份 HTML。

不要把子代理输出当作多份独立最终报告交付。除非用户明确要多个文件，最终产物必须整合并存为一个 Markdown 文件和一个 HTML 文件。

推荐风格（图优先 + 必要文字锚点）：

```text
<Mermaid sequence：UI 点击 -> page_x_event_cb() -> driver_set_mode() -> i2c_write_reg()>
状态：device_state.mode 由 page_x_event_cb() 写、refresh_timer_cb() 读。
验证：模拟器可验 UI 跳转；I2C 总线行为需硬件。
```

避免：

```text
UI 模块调用了驱动模块。
```

对每条用户选定功能路径，覆盖：触发、调用链（具体函数/文件顺序）、状态/数据、边界（应用→BSP/HAL/驱动/中间件/平台）、失败点、验证方法。

## 状态与归属

识别核心状态载体及其所有者。例：`device_state_t`、RTOS 队列、pthread handle、DMA 缓冲、描述符表、寄存器影子结构、配置文件、构建产物。

对每个重要状态载体回答：谁初始化？谁写？谁读？是否跨任务/线程/ISR 边界共享？有何保护，或缺保护/未知？

## 并发与事件

不要只列「存在 pthread/RTOS/定时器/中断」。要说明它们与主执行路径如何交互。检查清单：主循环/调度器所有者、任务/线程创建位置、ISR/回调/定时器入口、队列/消息/信号量/互斥量用法、阻塞调用与轮询、跨上下文共享状态、哪些可在模拟器验证、哪些必须上目标硬件。

## 架构词汇

用契合项目的分层：应用层、BSP、HAL/LL/寄存器层、驱动层、中间件/协议栈、RTOS/调度器、bootloader/升级层、构建与工具层、文档/RAG/支持工具层。

## 实现路径示例

固件：

```text
加一个 I2C 传感器：
1. 在 <文件> 确认 I2C 实例与引脚。
2. 在 <目录> 下加驱动。
3. 从 <函数> 初始化。
4. 用 <测试/构建/脚本> 验证。
```

工具：

```text
加一个新文档解析器：
1. 在 src/parsers/ 下加解析器类。
2. 在 src/parsers/__init__.py 注册扩展名。
3. 在 tests/ 下加解析器测试。
4. 用 CLI index/search 验证。
```

## 证据不堆砌

不要每句都引。在章节要点或表行级引用，让工程师读得顺。例如只引用起始函数、关键交接函数、最终驱动/平台函数，而非每行都引。
