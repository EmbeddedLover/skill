# 报告输出模板（Output Template）

本文件定义 `embedded-project-intake` 最终报告的**结构与排版规范**。核心原则四条，所有报告必须遵守：

1. **中文标题**：章节标题用中文；`Project Picture` / `AI Handoff Summary` 等专有名作英文副标题或括注，便于跨 agent 一致；证据标签 `CONFIRMED` / `INFERRED` / `UNKNOWN` / `CONFLICT` / `UNVERIFIED` 仍用英文（定义词汇）。
2. **图优先**：能用图就不用文字。调用关系（函数间、跨模块、任务/队列/回调）一律优先用 Mermaid（`flowchart` / `sequenceDiagram` / `stateDiagram-v2`）表达；文字只做补充说明与工程后果。**每个模块至少 2 张图**（模块架构图 + 实现调用关系图）。每张图后跟 2–5 条工程后果。图节点必须对应真实 文件 / 函数 / 模块 / 状态对象 / 任务 / 队列 / 硬件边界。
3. **目录**：标题之后紧跟 `## 📑 目录`，用 Markdown 锚点链接到各章节。
4. **按模块分层**：报告主线为「总体架构 → 每个模块的架构 → 每个模块的实现 → 跨模块流程 → 横切关注点」。同类琐碎模块（如 100+ 块板卡）合并为一条，避免噪声。

---

## Stage 1：候选路径检查点

`normal` / `deep` 模式下，除非用户已指定路径、授权自动选择或要求全量分析，否则先输出本检查点并**暂停等待用户选择**，不得包含完整最终报告。

```text
项目画像：<一句话，标 CONFIRMED/INFERRED + 项目类型>

候选路径：
1. <短标题> — <一句理由>
2. <短标题> — <一句理由>
3. <短标题> — <一句理由>

候选路径表：
| 候选路径 | 为何重要 | 证据入口 | 下游模块 | 建议优先级 | 深挖成本/风险 |
```

然后问一个直接问题：

```text
本轮深挖哪些路径？回复编号如 `1,3,5`；回复 `auto` 由我按变更风险与中心性选择；或回复 `full` / `all` / `全量分析` 做全量分析。
（本轮选定路径将在「四、选定路径深挖」以端到端调用关系图展开。）
```

---

## Stage 2：最终报告大纲

用户选定路径、选择 `auto` 或要求全量分析后按下述结构输出。把所选路径标为 `USER-SELECTED`、`AI-SELECTED` 或 `FULL-ANALYSIS`。最终报告既是工程师可读的项目文档，也是未来 AI 的交接件。

硬性要求：

- 必须包含**整体项目基线分析**（身份 / 架构 / 模块图 / 运行时流程 / 构建·运行·部署 / 风险 / 未知 / 阅读顺序）。
- 必须包含**所选或全量路径的深度分析**（函数级路径 / 状态·数据流 / 并发 / 风险 / 实现指引）。
- 必须有**至少**：总体架构图、运行时流程图、每个模块的架构图 + 实现调用关系图、每条选定路径的端到端调用关系图。
- **禁止**只输出所选路径深挖而缺少整体基线。
- 多路径只出**一份整合报告**，不拆成多个文件。

保存为项目内 Markdown，优先：

```text
docs/embedded-project-intake-<topic>.md
```

Markdown 是事实来源产物（人可读、AI 可复用）。图用 Mermaid 代码块（GitHub / VSCode / Typora 原生渲染）。HTML 是**必选派生产物**，每次最终报告都必须生成；生成 HTML 前先读 `references/html-report-output.md`。HTML 存于 Markdown 同目录：

```text
docs/embedded-project-intake-<topic>.html
```

最终聊天回复只需给 Markdown + HTML 两个路径 + 一句最关键风险/证据缺口，不要把报告或 HTML 源码贴进聊天。

### 一、项目总览

#### 1.1 项目一句话画像（Project Picture）

一句话，标置信度与项目类型（固件 / 固件支持工具 / BSP / 驱动示例 / bootloader / 文档·RAG 工具）：

```text
这是一个 <置信度> 的 <项目类型>，面向/支持 <目标或 UNKNOWN>，用 <构建系统或 UNKNOWN> 构建，基于 <SDK/RTOS/框架或 UNKNOWN>。
```

#### 1.2 技术栈与关键依赖

一张证据表：

```text
维度 | 内容 | 证据（file:line） | 状态
MCU/芯片 | ... | sdkconfig.defaults.* / Kconfig | CONFIRMED/UNKNOWN
构建系统 | ... | CMakeLists.txt | CONFIRMED
SDK/RTOS | ... | idf_component.yml | CONFIRMED
关键依赖 | ... | idf_component.yml / package | CONFIRMED
```

#### 1.3 AI 交接摘要（AI Handoff Summary）

置顶、紧凑，可整体粘贴进下个 AI 会话。结构：

```text
Project Root: <路径>
Project Identity: <确认/推断的身份>
Build/Run Entry: <命令/脚本/产物>
Deep-Dive Scope: <USER-SELECTED / AI-SELECTED / FULL-ANALYSIS 列表>
Core Architecture: <一段紧凑描述>
Critical Files: <文件 → 为何重要>
Main Runtime Flow: <入口 → 初始化 → 调度/主循环/任务>
Key State/Data: <状态载体 → 写者/读者>
Concurrency/Event Model: <线程/任务/中断/定时器/回调与通信>
Hardware/Platform Boundaries: <BSP/HAL/驱动/平台跨越点>
Main Risks: <3-7 条>
Unknowns: <需用户/构建日志/手册/原理图/硬件补全项>
Next Best Actions: <带起始文件的具体下一步>
```

规则：优先用稳定的 文件/函数 锚点而非纯散文；不含证据的结论不得出现；比正文短，细节放后文；自洽到下一个 AI 可直接从此开工。

### 二、总体架构

工程语言解释：顶层分层、主控制路径、数据路径、硬件抽象边界、外部依赖。每个分层都要有证据。

#### 2.1 分层架构总览图

`flowchart TD`：顶层分层 + 平台边界 + 主要三方依赖。图后 2–5 条工程后果。

#### 2.2 模块全景

一张 `flowchart`/`graph` 展示模块间依赖与数据流向，加一张模块清单表：

```text
模块/目录 | 职责 | 关键文件 | 主入口 | 依赖 | 证据
```

若职责由名字/符号推断，标 `INFERRED`。

#### 2.3 启动与主运行时流程

`sequenceDiagram`：reset → 启动 → 系统初始化 → main → 调度器/主循环/任务。工具类项目则是 CLI/MCP/API 入口 → 解析/索引/存储/检索 → 输出。用箭头与文件/函数引用：

```text
entry_a() -> module_b.function() -> module_c.function()
```

#### 2.4 关键平台边界

说明应用代码在何处跨越进 BSP / HAL / 驱动 / 中间件 / 平台。给出边界文件与函数。

### 三、模块详解 ★核心章节

对每个**重要/核心模块**单独成节（`3.x`）。同类琐碎模块合并为一条（例：100+ 块板卡 → 「板级适配层」一条，内部分组说明）。

每个模块节**必须**包含以下小节，且**至少 2 张 Mermaid 图**：

```markdown
### 3.x <模块名>

#### 模块架构图
<Mermaid flowchart：该模块内部结构 + 直接上下游模块/驱动>
<图后 2-5 条工程后果>

#### 职责与边界
<1-2 句职责 + 证据 file:line>

#### 实现与调用关系图   ← 「每个模块的实现」，图示优先
<Mermaid flowchart/sequence：该模块内的函数级调用与数据流>
<配合精简文字说明关键调用链：trigger -> handler -> driver -> 寄存器/总线>

#### 关键文件与入口
| 文件 | 入口函数/类 | 证据 |
|---|---|---|

#### 状态/数据与对外接口
<模块持有的核心状态、对外暴露的接口、与其他模块的数据交换>

#### 风险点与验证
<该模块的风险 + 如何验证（编译/上板/日志/抓包）>
```

> 原则：实现与调用关系**优先用图**；只有图无法表达（如纯配置/枚举）才退回文字调用链。

### 四、选定路径深挖（Feature Call Paths）

追踪**用户选定**、`auto` 自动选择或 `full/all/全量分析` 覆盖的路径。有源码时，normal/deep 报告此节**必填**。全量分析不等于无限展开所有文件；它表示覆盖所有有工程意义、能被证据支持的核心业务/技术路径，并把低价值重复路径合并说明。

每条路径：

```markdown
### 路径 N — <路径名> <USER-SELECTED/AI-SELECTED/FULL-ANALYSIS>

#### 端到端调用关系图
<Mermaid sequence/flowchart：跨模块的函数/状态/队列/回调/硬件边界>
<图后工程后果>

#### 路径细节
- 触发点：reset / 主循环 / CLI / UI 事件 / 数据包 / IRQ / 定时器 / 队列消息 / 回调
- 调用链：具体函数/文件顺序（trigger -> ... -> 边界 -> 驱动）
- 状态/数据：结构体/全局/缓冲/配置/寄存器/handle/队列/消息/产物
- 平台边界：应用→BSP/HAL/驱动/中间件/平台的跨越点
- 失败点：超时 / 分配 / 硬编码路径 / 竞态 / 缺锁 / 阻塞调用 / 未检返回值 / 非法配置 / 协议失配
- 验证：仅编译 / 模拟器 / 单测 / 日志 / 硬件探针 / 串口 / 抓包 / 调试器 / 上板测试
```

紧凑表汇总（可选）：

```text
特性 | 选择标记 | 触发 | 函数/文件路径 | 状态·数据 | 平台边界 | 失败点 | 验证
```

无法追踪的路径标 `UNKNOWN`，并说明缺什么（源码 / 生成文件 / 日志 / 原理图 / 手册）。

### 五、状态归属与并发模型

#### 5.1 核心状态/数据归属表

```text
状态/数据 | 初始化者 | 写入者 | 读取者 | 跨上下文? | 保护/隐患 | 证据
```

覆盖全局、配置文件、RTOS 队列、pthread 队列、ISR 缓冲、DMA 缓冲、协议包、handle、描述符、构建产物。

#### 5.2 并发与事件模型

先用**图**展示各执行上下文（主循环/调度器、任务、中断、DMA 回调、定时器、轮询、回调注册表）如何交互，再用表补充：

```text
上下文 | 创建/进入处 | 工作 | 通信方式 | 共享状态 | 验证备注 | 证据
```

不要只列「存在 pthread/RTOS/中断」，要说明它们与主执行路径如何交互、哪些可在模拟器验证、哪些必须上板。

## 排版细则

- Mermaid 图保持简洁，过密则拆成多张；每张图节点必须对应报告中已命名的真实 文件/函数/模块/状态/任务/队列/硬件边界/产物。
- 证据在「行/路径」级别引用即可，不必每句都引；在章节要点或表行级引用，保证工程师读起来顺畅。
- 不要为视觉整洁删除 unknowns / conflicts / 低置信结论。
- 不要把有证据的工程陈述改写成含糊散文。
- 每张 Markdown 表都要在 HTML 中有对应 `<table>`；表过宽则横向滚动，不删列。
