## 26 个代表性模板

| 模板 | 核心输入 | 预期结果与关键门禁 |
|---|---|---|
| 产品想法澄清 | 用户、场景、痛点、实体交互、目标价格 | 区分事实/假设/待确认；先收敛最小价值，不直接选芯片 |
| 技术可行性初判 | 核心功能、环境、体积、供电、周期 | 给出可行/有条件可行/不可行、主要阻塞和最小 PoC |
| PRD 产品需求整理 | 产品目标、用户旅程、MVP 边界 | 需求可验收；硬件、固件、生产和认证约束不遗漏 |
| 硬件需求整理 | 供电、接口、传感、执行、环境、成本 | 形成可冻结约束表，未知项不猜测 |
| 系统框图生成 | 功能域、数据流、控制流、电源流 | 模块职责和跨域接口明确，未知连接单独标记 |
| MCU / SoC 选型 | IO、外设、RAM/Flash、算力、功耗、生态 | 至少给候选与余量，参数必须有当前证据和替代路径 |
| 接口资源分配 | 精确 MCU、原理图、Pin Map、外设需求 | 输出 Pin/AF/DMA/IRQ 表并检查复用、调试口和电压冲突 |
| 电源架构设计 | 输入范围、负载、峰值、时序、热和保护 | 电源树、最坏电流预算、效率/热、启动和异常路径 |
| AI 修改边界确认 | 工程结构、生成器、已验证代码、目标任务 | 列 Allowed Files、保护区、风险和最小验证；边界外不写 |
| 固件工程接入 | 构建文件、启动/链接、SDK、入口、脚本 | 形成带证据的 Project Profile，不把目录名当事实 |
| 固件分层架构 | 需求、现有模块、硬件接口、约束 | 明确 BSP/Driver/Service/App 依赖方向和模块契约 |
| RTOS 任务架构 | 周期、deadline、事件、共享资源、内存 | 任务、优先级、栈、队列/锁、ISR 交接和超时恢复 |
| 固件改动影响分析 | Diff、调用图、资源表、接口、验证记录 | 列行为、时序、并发、内存、功耗、回归和回滚影响 |
| 单元测试接入 | 模块边界、构建系统、现有框架、硬件依赖 | 选择主机测试边界、Mock/Stub、用例矩阵和可运行命令 |
| 电源原理图评审 | 原理图、器件额定值、负载和时序 | 检查路径、极性、裕量、环路、保护、上电和测量点 |
| I2C 控制器 | 地址、速率、电平、上拉、并发、器件协议 | 超时、NACK、总线恢复、重试边界和逻辑分析仪判据 |
| 状态机框架 | 状态、事件、条件、动作、异常和超时 | 完整转移表，避免隐藏状态、丢事件和不可恢复分支 |
| 上电无反应排查 | 电源、时钟、复位、Boot、调试和日志 | 从电源到 CPU 执行逐层排查，每一步给测量点和判据 |
| EVT 测试计划 | 需求、风险、样机版本、设备和环境 | 测试项、步骤、Pass/Fail、证据、负责人和阻塞项 |
| 回归测试清单 | 变更范围、历史问题、依赖模块 | 风险驱动选择回归集，不只验证改动点的正向路径 |
| 功耗预算 | 各模式电流、占空比、电池、电源效率 | 典型/最坏预算、续航、峰值压降和实测计划 |
| 可靠性测试计划 | 环境、寿命、应力、使用模型 | 温循、振动、ESD、长稳、掉电等可量化判据 |
| 安全风险评审 | 资产、接口、升级、密钥、物理访问 | 威胁、影响、控制、残余风险和验证方法 |
| 产测总体方案 | 工序、节拍、接口、校准、追溯、不良定位 | 测试覆盖、治具、烧录、序列号、日志和失败分流 |
| OTA 风险评审 | Bootloader、分区、签名、电源/网络故障 | 回滚、防降级、断电恢复、兼容性和灰度策略 |
| 现场问题分析 | 版本、复现率、环境、日志、批次、变更史 | 事实时间线、假设树、证据请求、止血/根因/回归闭环 |

## 可复用的 Prompt 合同

VibeBoard 不需要保存大量相互独立的长 Prompt，更适合把共同要求实现为系统级合同：

```text
目标：把用户自然语言收敛为一个最小可验证硬件任务。

证据：先读取项目、原理图、手册、构建配置和日志；每个关键结论引用来源。
事实状态：CONFIRMED / INFERRED / UNKNOWN / CONFLICT / UNVERIFIED。
禁止猜测：精确料号、封装、内存、时钟、电压、引脚、极性、烧录范围、探针和端口。
修改边界：只写本轮允许文件；厂商/生成器/已上板代码默认保护。
实现策略：定义验证 -> 最小增量 -> 构建 -> 明确目标后烧录 -> 采集硬件证据。
异常策略：停止扩展，保存日志和产物，返回失败类别、下一条最小诊断动作和回滚方案。
完成条件：不能以“代码已生成”结束；必须报告构建、板级测量或明确的未验证状态。
```

## Prompt 设计启示

- 高成功率来自上下文合同、门禁和证据回写，不来自把 Prompt 写得更长。
- 对重复字段使用结构化 Schema，对领域差异使用短的 Skill/Policy 插件。
- 用户问题应只覆盖当前阻塞项；已经能从工程或资料确认的内容不要重复询问。
- 对原型和量产应提供不同风险策略：原型可快速假设，量产必须冻结约束并逐项留痕。
